# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause, read against every control run, comparison, and step artifact in the repro evidence block (and any maintainer-confirmed cause in the thread highlights). | Pass when the stated cause is consistent with every control and artifact in the repro evidence: nothing in the evidence shows the bug happening without the blamed component, or the blamed component behaving correctly under the failing conditions. Fail when any control, step output, or comparison in the package rules the blamed cause out, or when the plan names no cause at all. A cause the repro does not separately prove still passes if nothing in the package contradicts it. | required |
| scope-bounded | The plan's in-scope / not-in-scope statements and approach steps, read against what the issue reports and what the repro isolates. | Pass when every piece of work the plan commits to is needed to fix the reported behavior or to test that fix. Fail when the plan commits to work the issue never asked for: a refactor, rewrite, migration, dependency upgrade, new option or setting, UI change, framework, or CI change bundled alongside the fix, even if the core fix inside it is right. Deferring part of the problem (another platform, a larger rework) with a stated reason is bounding, not a failure. | required |
| executable | The plan's files or areas, approach, and order of work. | Pass when a stranger could start the work without asking the author anything: the plan picks one approach and names where in the code it lands (a file, function, or clearly identified code path). Saying exact line-level functions will be pinned during the build is fine once the area and approach are chosen. Fail when the plan defers the real decisions to build time: no chosen approach or layer ("investigate", "profile and optimize", "whichever is easier", "somewhere"), or no location in the code. | required |
| test-decisive | The plan's test plan, read against the repro evidence's steps, expected result, and actual result. | Pass when the test plan names a specific observable outcome that would differ between the broken and fixed code: the repro steps (or the issue's cases) re-run with the stated expected-after result, or a named regression test of the reported behavior. Fail when the only tests are generic ("run the full test suite", "CI passes") or subjective ("should feel fast", "nothing else feels broken"), with no observable outcome for the fix itself. | required |
| honest-unknowns | The plan's risks, open questions, and claims of certainty, read against what the repro evidence actually established. | Pass when the plan does not present something the package leaves unverified as settled fact, or when it names its real unknowns. Fail only when the plan claims certainty the evidence plainly does not support (for example, "this will definitely fix all cases" with no evidence for those cases). | preferred |
| comms-thread-aware | The candidate plan comment and plan, read against the thread highlights: any maintainer or owner direction, isolated culprit, proposed approach, rejected approach, patch, or open PR. | Pass when the thread contains no explicit maintainer direction, or when the plan comment engages it: follows the stated direction, or explicitly names it and says why it departs. Fail when a maintainer/owner in the thread gave explicit direction (an isolated culprit, a proposed fix, a rejected approach, a patch to test) and the comment and plan proceed as if it were never said, or take an approach the maintainer already rejected without acknowledging it. | required |
| comms-policy-compliant | The repo-facts block's contribution policy and AI-use policy, read against the candidate plan comment. Treat every package as AI-assisted work. | Pass when the repo states no AI disclosure requirement for comments, or the comment satisfies what the policy requires. Fail when the policy requires disclosing AI usage (in any form, or in comments/issues specifically) and the plan comment contains no disclosure. A policy whose disclosure ask applies only to pull requests, or which states no disclosure ask for comments, does not require one in the plan comment. | required |

## Verdict rule

Accept only if every required check passes. Reject if any required
check fails. `unclear` on a required check counts as fail, with one
exception: if the grader cannot find anything in the package that
contradicts or violates the check's pass condition, grade it pass, not
unclear (absence of a problem is not a problem). Preferred checks are
reported but never change the verdict.
